# ZIP روزانه یا سالانه BIN → Hugging Face

لینک ZIP را به Actions بدهید؛ حالا **یک BIN سالانه، چند BIN روزانه، چند فایل چندروزه یا ترکیبی از آن‌ها** پذیرفته می‌شود. خروجی همیشه روزانه در پوشهٔ همان نماد داخل هاگینگ‌فیس است و `index.txt` به‌روز می‌شود. همهٔ BINهای انتخاب‌شده باید متعلق به **یک نماد** باشند. نیازی به روشن‌ماندن گوشی/کامپیوتر نیست؛ Release ساخته نمی‌شود.

## اجرا
1. Secret موجود `HF_TOKEN` با دسترسی نوشتن به دیتاست مقصد کافی است. مقصد پیش‌فرض `Esmaeil9ss/Tickdata`؛ تغییر با Variable به نام `HF_DATASET`. دیتاست و ایندکس BRIDX1 معتبر باید از قبل موجود باشند.
2. Actions → **ZIP daily or annual BIN to HF** → یک **Run workflow جدید روی main**. Re-run اجرای قدیمی کد قدیمی را اجرا می‌کند.
3. `zip_url`: لینک مستقیم عمومی HTTPS. لینک امضاشده/محرمانه را در Secret به نام `SOURCE_ZIP_URL` بگذارید و ورودی را خالی بگذارید؛ توکن را در چت یا کد نگذارید.
4. `symbol`: نماد واقعی همهٔ فایل‌های انتخابی، مثلاً EURUSD. هیچ نمادی از روی قیمت‌ها قابل تشخیص قطعی نیست. ZIP چندنمادی را یک‌جا وارد نکنید.
5. **`member` را خالی بگذارید تا تمام فایل‌های `.bin`/`.BIN` حتی داخل زیرپوشه‌ها پردازش شوند.** برای فقط یک فایل، مسیر دقیق داخل ZIP را بدهید. فایل‌های غیر BIN نادیده گرفته می‌شوند.
6. `digits`: برای EURUSD مقدار 5، برای USDJPY مقدار 3؛ فقط برای SYM جدید است و متادیتای نماد قبلی حفظ می‌شود.
7. `confirm_complete_days`: فقط پس از بررسی کامل‌بودن منبع روشن شود؛ اسکریپت نمی‌تواند گم‌شدن ساعات منبع را صرفاً از timestamp اثبات کند.
8. `replace_existing`: پیش‌فرض خاموش؛ فقط برای بازنویسی آگاهانهٔ روزهای موجود روشن کنید. این گزینه تعارض بین فایل‌های داخل ZIP را مجاز نمی‌کند.

## مثال ZIP روزانه
```text
EURUSD.zip
  data/EURUSD_2026-10-07.BIN
  data/EURUSD_2026-10-08.BIN
  data/EURUSD_2026-10-09.BIN
```
با symbol=EURUSD و member خالی، مقصد:
```text
EURUSD/EURUSD_2026-10-07.BIN
EURUSD/EURUSD_2026-10-08.BIN
EURUSD/EURUSD_2026-10-09.BIN
```
برای فایل سالانه نیز member خالی کافی است؛ تقسیم بر اساس **timestamp واقعی UTC هر تیک** انجام می‌شود. نام روزانهٔ استاندارد `SYMBOL_YYYY-MM-DD.BIN` باید با نماد ورودی و روز واقعی داده تطبیق داشته باشد؛ فایل روزانه با تاریخ اشتباه رد می‌شود. نام سالانه مبنای تقسیم نیست و عبور واقعی داده از مرز سال پشتیبانی می‌شود.

## ایمنی و روزهای تکراری
- همهٔ اعضای انتخابی ابتدا اعتبارسنجی می‌شوند؛ خرابی حتی آخرین فایل یعنی **هیچ آپلودی شروع نمی‌شود**. stage ناقص پاک می‌شود.
- فایل‌ها لازم نیست در ZIP به ترتیب روز باشند، ولی تیک‌های هر فایل باید مرتب باشند. تیک‌های با میلی‌ثانیهٔ برابر حفظ می‌شوند.
- اگر چند عضو یک روز مشترک دارند، فقط در صورت برابری SHA256، اندازه و تعداد تیکِ خروجی روزانه، یک نسخه نگه داشته و منابع در گزارش ثبت می‌شوند. در غیر این صورت متوقف می‌شود؛ دو قسمت جدا از یک روز خودکار به هم چسبانده نمی‌شوند. حتی تفاوت بلوک‌بندی خروجی ممکن است به‌صورت محافظه‌کارانه تعارض شناخته شود.
- خروجی روزانه با همان ساختار استاندارد بازنویسی می‌شود؛ ممکن است بلوک‌بندی نسبت به فایل ورودی متفاوت باشد ولی مقادیر و ترتیب تیک‌ها حفظ می‌شوند.
- BIN باید bin_v1 بارریپلی باشد: بلوک‌های little-endian شامل int32 count، int64 UTC ms[count]، float64 Bid[count]، float64 Ask[count]. هر پسوند BIN دلخواه، MqlTick خام و CSV تغییرپسوندی پذیرفته نیست. قیمت متناهی، Bid>0 و Ask>=Bid الزامی است.
- روز جاری UTC در حالت آپلود رد می‌شود؛ روز بدون تیک ساخته نمی‌شود. فایل صفر‌بایتی/بدون تیک در ZIP رد می‌شود، نه اینکه خودکار به‌عنوان روز تعطیل فرض شود.
- extractall نداریم؛ فایل‌های سالانه کامل جداگانه استخراج نمی‌شوند. همان خواندن بلوکی و بخش‌های 100000 تیکی استفاده می‌شود؛ بلوک بزرگ ورودی موقتاً روی دیسک قرار می‌گیرد. مسیر خطرناک، symlink، ZIP رمزدار، نام عضو تکراری و نسبت فشرده‌سازی مشکوک رد می‌شوند.

## آپلود و محدودیت‌ها
فایل روزانه، audit منبع و index هر دستهٔ حداکثر 30 روزه در یک commit با parent_commit ثبت می‌شوند. مسیرها و SYMهای قبلی حفظ می‌شوند. فایل موجود و ثبت‌شده skip می‌شود؛ ورودی ایندکس مفقود برای فایل موجود فقط پس از تطبیق محتوا تعمیر می‌شود. محتوای متفاوت نیازمند بررسی/جایگزینی عمدی است. commit بدون تغییر با already_unchanged گزارش می‌شود، نه uploaded. news manifest و summary دست‌کاری نمی‌شوند.

سقف پیش‌فرض ZIP سه GiB و **مجموع اندازهٔ بازشدهٔ همهٔ BINهای انتخابی شش GiB** است؛ سقف به ازای هر فایل جدا نیست. حداکثر 10000 BIN انتخابی. زمان job حدود 350 دقیقه؛ ZIP، خروجی‌ها و بلوک موقت باید روی دیسک جا شوند. دانلود سه تلاش محدود دارد و resume ندارد. نیاز به لینک عمومی HTTPS، منبع مورداعتماد و مجوز بازنشر داده دارید؛ کنترل DNS/redirect جای sandbox کامل نیست. پروژهٔ نویسندهٔ دیگری را هم‌زمان روی همان دیتاست اجرا نکنید.

اگر دستهٔ آپلود بعدی شکست بخورد، دسته‌های قبلی باقی می‌مانند؛ اجرای مجدد با replace_existing خاموش آن‌ها را skip می‌کند. منبع ZIP/BIN به GitHub Artifacts فرستاده نمی‌شود؛ فقط گزارش‌ها 7 روز نگه‌داری می‌شوند. گزارش شامل نام فایل‌های منبع، روزها، تعداد تیک و SHA است و در مخزن عمومی می‌تواند قابل‌مشاهده باشد. لینک محرمانه را در Secret نگه دارید. هیچ پرداخت یا سرویس پولی فعال نمی‌شود؛ محدودیت‌ها و سهمیه‌های GitHub/HF برقرارند.

## اجرای محلی
Python 3.11+:
```bash
pip install -r requirements.txt
python -m unittest discover -s tests -t . -v
python import_collection.py --zip data.zip --symbol EURUSD --digits 5
```
آپلود با HF_TOKEN در محیط امن:
```bash
python import_collection.py --zip data.zip --symbol EURUSD --digits 5 --upload --confirm-complete-days
```
`import_collection.py` ورودی جدید و فعال workflow است؛ `import_zip.py` به‌عنوان موتور قدیمیِ تک‌فایلی حفظ شده است.

## آزمون
20 تست جدید آفلاین با ZIP واقعیِ ساخته‌شده، روزانه/سالانه/ترکیبی، پوشهٔ تو‌در‌تو، تکرار یکسان، تعارض، نام/تاریخ غلط، سقف مجموع، مسیر خطرناک، تیک هم‌زمان و آپلود شبیه‌سازی‌شدهٔ BIN+index پاس شدند. تست‌های قبلی حفظ شده‌اند و Actions همه را اجرا می‌کند. دانلود زنده از لینک شما و آپلود واقعی به حساب HF در این تغییر اجرا نشده‌اند؛ ابتدا با یک ZIP کوچک آزمایش کنید.
