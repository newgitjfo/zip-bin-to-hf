# ZIP annual BIN → daily BIN → Hugging Face

لینک دانلود مستقیم ZIP را به GitHub Actions بدهید؛ سرور GitHub آن را دانلود می‌کند و یک فایل BIN سالانه داخلش را بر اساس **زمان واقعی هر تیک UTC** به BINهای روزانه تبدیل و در هاگینگ‌فیس آپلود می‌کند. نیازی به روشن‌ماندن گوشی یا کامپیوتر شما نیست. GitHub Release یا خروجی CSV ساخته نمی‌شود.

## راه‌اندازی
1. Settings → Secrets and variables → Actions: یک Secret به نام **HF_TOKEN** با توکن fine-grained دارای اجازه نوشتن فقط روی دیتاست مقصد بسازید. توکن را داخل کد، چت یا URL قرار ندهید. Secret مخزن دیگر خودکار منتقل نمی‌شود.
2. مقصد پیش‌فرض **Esmaeil9ss/Tickdata** است. برای تغییر، Actions Variable به نام **HF_DATASET** بسازید. دیتاست و index.txt معتبر BRIDX1 باید از قبل وجود داشته باشند؛ ابزار آن‌ها را ایجاد نمی‌کند.
3. Actions → **ZIP annual BIN to daily HF files** → Run workflow.
4. zip_url: لینک مستقیم HTTPS دانلود ZIP. لینک صفحه وب یا نیازمند ورود مرورگر کافی نیست. اگر لینک query محرمانه/امضاشده دارد، آن را در Secret به نام **SOURCE_ZIP_URL** بگذارید و فیلد zip_url را خالی بگذارید؛ ورودی workflow را محل امن نگه‌داری لینک محرمانه فرض نکنید.
5. symbol: نماد واقعی فایل، مثلاً USDJPY. نماد از قیمت‌ها یا نام فایل قابل اثبات نیست؛ اشتباه وارد نکنید.
6. member: اگر ZIP فقط یک BIN دارد خالی بگذارید؛ در غیر این صورت مسیر دقیق مثل `data/USDJPY_2025.BIN` را بدهید. در هر اجرا فقط یک BIN انتخاب می‌شود؛ در چند اجرای جدا می‌توانید اعضای دیگر را وارد کنید.
7. digits: برای USDJPY مقدار 3 و EURUSD مقدار 5؛ فقط هنگام ساخت SYM جدید استفاده می‌شود و قیمت‌ها تغییر مقیاس نمی‌دهند. SYM قبلی حفظ می‌شود.
8. confirm_complete_days: فقط وقتی منبع برای روزهای موردنظر کامل است روشن کنید. اسکریپت از زمان اولین/آخرین تیک به‌تنهایی نمی‌تواند ساعات گمشده منبع را اثبات کند.
9. replace_existing: پیش‌فرض خاموش، فایل موجود رد می‌شود؛ روشن فقط برای بازنویسی آگاهانه روزهای هم‌نام.

## فرمت پشتیبانی‌شده
این ابزار برای هر فایلی با پسوند BIN نیست. ورودی باید **bin_v1 فعلی BarReplay** باشد: یک یا چند بلوک، هر بلوک int32 تعداد، int64 زمان UTC میلی‌ثانیه[]، float64 Bid[] و float64 Ask[]؛ همگی little-endian. سرآیند magic دیگری، رکوردهای MqlTick خام، CSV تغییرپسوندی و BIN دارای ساختار دیگر پشتیبانی نمی‌شود. اگر فرمت ناسازگار باشد، متوقف می‌شود و آپلود نمی‌کند.
تیک‌ها باید در کل فایل به ترتیب غیرکاهشی زمان باشند. تیک‌های متفاوت با میلی‌ثانیه برابر حفظ می‌شوند؛ حذف تکراری خودکار نداریم. قیمت باید متناهی، مثبت و Ask>=Bid باشد. ورودی منبع با قیمت‌های crossed نیاز به بررسی جداگانه دارد و خودکار اصلاح نمی‌شود.

## روزبندی و خروجی
مثال مسیر مقصد: `USDJPY/USDJPY_2025-09-24.BIN`. روز از timestamp هر تیک تعیین می‌شود؛ نام فایل سالانه یا تاریخ پایان چانک مبنای تقسیم نیست. حتی اگر یک بلوک از نیمه‌شب یا سال جدید عبور کند درست تقسیم می‌شود. روز بدون تیک فایل ساختگی نمی‌گیرد. روز جاری UTC در حالت آپلود رد می‌شود. تعداد بلوک‌های فایل روزانه ممکن است با نسخه سالانه متفاوت باشد ولی ترتیب و مقادیر تیک‌ها حفظ می‌شود.
هیچ extractall انجام نمی‌شود؛ فقط عضو BIN انتخابی مستقیم از ZIP بازفشرده و بلوک‌به‌بلوک پردازش می‌شود. نسخه کامل سالانه جداگانه روی دیسک ساخته نمی‌شود. مصرف RAM به قطعه‌های 100000 تیکی محدود است؛ هر بلوک ورودی موقتاً روی دیسک نگه داشته می‌شود. نام‌های مسیر خطرناک، عضو symlink، ZIP رمزدار و فایل‌های خارج از سقف رد می‌شوند.

## آپلود و فهرست
پس از اعتبارسنجی کل عضو انتخابی، فایل‌های روزانه در دسته‌های حداکثر 30 روزه ثبت می‌شوند؛ BIN، گزارش روز و index.txt هر دسته یک commit اتمی دارند. مسیرها و مشخصات قبلی فهرست حفظ می‌شوند؛ خطای خواندن فهرست یا فرمت ناشناخته موجب توقف است، نه جایگزینی با فهرست خالی. کنترل parent_commit از گم‌شدن تغییرات نویسنده دیگر جلوگیری می‌کند؛ concurrency فقط همین مخزن را صف‌بندی می‌کند. با دیگر پروژه‌های نویسنده همان دیتاست هم‌زمان اجرا نکنید.
اندازه و SHA256 هر روز پیش از آپلود بررسی می‌شود. موجودبودن فایل در HF پیش‌فرض باعث ردشدن می‌شود حتی اگر حجم متفاوت باشد. فایل موجود ولی ثبت‌نشده در index نیازمند بررسی دستی است؛ این پروژه بازسازی کلی 2865 ورودی قدیمی یا summary کش‌شده وورکر را انجام نمی‌دهد.
اگر دسته‌ای موفق و دسته بعدی ناموفق شود، ثبت قبلی باقی می‌ماند. اجرای مجدد با replace_existing خاموش آن‌ها را رد می‌کند. تعارض و خطای commit خودکار با فهرست قدیمی تکرار نمی‌شود. خطای منبع قبل از اتمام split هیچ آپلودی انجام نمی‌دهد.

## محدودیت‌ها و هزینه
Workflow فقط دستی است؛ بعد از انتشار مخزن هیچ دانلود/آپلودی خودکار شروع نشده است. مهلت job حدود 350 دقیقه، سقف پیش‌فرض ZIP سه GiB و BIN بازشده شش GiB است. مجموع ZIP + خروجی روزانه + بزرگ‌ترین بلوک باید روی دیسک runner جا شود؛ ZIP زیر سقف هم ممکن است به علت فضای دیسک رد شود. تغییر سقف‌ها با فلگ خط فرمان ممکن است اما ظرفیت runner افزایش نمی‌یابد. برای فایل بزرگ‌تر به runner با فضای بیشتر نیاز دارید؛ این ابزار ZIP چندبخشی یا بایگانی رمزدار را باز نمی‌کند.
دانلود جریان‌دار و حداکثر سه تلاش روی خطای شبکه دارد؛ resume از وسط فایل ندارد و تلاش مجدد دانلود را از ابتدا شروع می‌کند. لینک باید عمومی و مستقیم باشد؛ کوکی ورود، رمز و سرور داخلی پشتیبانی نمی‌شود. کنترل عمومی‌بودن DNS و redirect انجام می‌شود ولی این ابزار جای sandbox امنیتی کامل برای ورودی دلخواه نیست. فقط لینک منبع مورداعتماد خودتان را استفاده کنید.
مخزن کد عمومی است؛ source ZIP و BINها به GitHub Artifacts فرستاده نمی‌شوند. فقط گزارش نام عضو، نماد، روزها، شمارش و SHA256 منتشر می‌شود و در مخزن عمومی ممکن است برای دیگران قابل‌دیدن باشد. محتوای داده طبق دسترسی خود دیتاست HF منتشر می‌شود. لینک‌های امضاشده را در Secret نگه دارید. مجوز بازنشر داده را بررسی کنید.
Runner استاندارد مخزن عمومی ممکن است تحت شرایط رایگان GitHub باشد؛ محدودیت زمان/فضا، نرخ HF و تغییر تعرفه‌ها برقرارند. پرداخت یا runner بزرگ‌تر خودکار فعال نمی‌شود؛ رایگان نامحدود تضمین نیست.

## اجرای محلی بدون آپلود
Python 3.11 یا جدیدتر:

```bash
pip install -r requirements.txt
python -m unittest discover -s tests -t . -v
python import_zip.py --zip annual.zip --symbol USDJPY --output work
```

آپلود محلی، فقط با HF_TOKEN امن در محیط:

```bash
python import_zip.py --zip annual.zip --symbol USDJPY --digits 3 --upload --confirm-complete-days
```

## وضعیت تست
تست‌های آفلاین با ZIPهای ساخته‌شده و BIN نمونه، مرز روز/سال، تیک‌های هم‌زمان، فرمت خراب، ترتیب نامعتبر و حفظ index را بررسی می‌کنند. دانلود از لینک واقعی شما، آپلود حساب شما و واردسازی MT5 هنوز تأیید نشده‌اند. اولین اجرا را با ZIP کوچک و چند روز انجام دهید. نتیجه گزارش در Artifacts و مسیرهای گزارش محلی است؛ فایل‌های خروجی محلی در پایان runner باقی نمی‌مانند، پس اگر آپلود ناموفق بود اجرای مجدد لازم است.
